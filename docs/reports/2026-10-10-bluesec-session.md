запросы модели и повторные проверки BlueSec не выполнялись.

## Что реализовано

- `v2` хранит полученные доказательства отдельно от ограниченного контекста модели.
  Различаются прочитанные объекты, ссылки на ещё не прочитанные объекты, типы ID и
  точные пути полей. История сохраняет ранее полученные свойства.
- Схемы инструментов берутся из runtime. JSON Schema и provenance проверяются
  перед отправкой. Исправление JSON ограничено числом попыток и временем.
- Приоритетный обход связей процесса, защита от повторных чтений, проверка
  оставшихся важных связей перед добровольным завершением и резерв финального ответа.
- Общий замок и durable intent между worktree, idempotency, ограниченные повторы
  и закрытие сессии. Неизвестный исход финального RPC сохраняет неопределённость;
  остановка процесса сама по себе не подтверждает закрытие сервера.
- Журналирование LLM/RPC, токенов, ошибок, происхождения доказательств, source SHA
  и cleanup. Неизвестный usage сохраняется как неизвестный.
- Офлайн-набор из 12 сценариев и средства сравнения ограниченных экспериментов.
  Он проверяет поведение обвязки; сам по себе не измеряет точность LLM.
- Независимые режимы `--quality-submit`, `--deadline-submit`, `--submission-only`.
  Последний сдаёт явно неполные ответы без модели и чтения графа.

Код и инструкции: [README](../../README.md), [quality.py](../../src/bluesec1_agent/quality.py),
[CLI](../../src/bluesec1_agent/cli.py), [план работы](../superpowers/plans/2026-10-10-goal-team.md).

## Последний прогон: версия и настройки

Запуск выполнен из чистого worktree на commit
`9fdf92cc0d9b80bdd77c9d757a43c2f08230f7f8`; исходники во время запуска не менялись.
Его изменения интегрированы в основную рабочую ветку коммитами `cd17085`,
`6f222d9`, `d3fa385`; `fd20546` добавил документацию и проверки политик транспорта.
Эти SHA различаются из-за интеграции. Для точного воспроизведения источника
используйте хеши файлов из [summary.json](quality-1555/summary.json).

| Параметр | Значение |
| --- | --- |
| Arena, модель | `graded`, запрошена `gpt-6-astra` |
| Scope | Ровно 40 задач, один процесс с доступом к runtime |
| Общий дедлайн | 12:55:00 UTC / 15:55:00 МСК |
| Лимиты шагов / evidence-контекста | 100 / 32 000 символов |
| Чтение графа | До 24 чтений, суммарно до 8 с, до 3 с на чтение |
| Бюджет расследования | До 60 с; пересчитывается для оставшихся задач |
| Получение задачи | allowance 8 с на задачу; timeout lease 20 с |
| Финал / закрытие | Резерв 9 с для финала; 35 с в общем бюджете на cleanup |
| Финальный RPC | До 8 с, дополнительно ограничен остатком бюджета задачи |
| Runtime retry | Одна попытка |
| LLM | До 4096 output tokens; до двух обращений: решение и исправление, если осталось время |
| Advisory | Только identity-matched ответ по текущему evidence brief; схема и provenance обязательны |

Приоритет отдаётся исходному процессу, в том числе если более поздняя пустая ссылка
перезаписала его текущий тип. Чтения связей перемежаются с чтением объектов соседей.
Модель получает ограниченный граф и выбирает только `finish_investigation`.
Файл advisory содержит ровно `run_id`, `task_id`, `evidence_sha256`, `decision`;
публикуется атомарно. Координатор даёт ответ, но не вызывает runtime.

## Обнаруженные ограничения

1. **Сбои провайдера.** С задачи `92f9f7e2` быстрые HTTP 400 приводили к двум
   неудачным попыткам и fallback раньше появления advisory. Тело ошибки не
   сохранялось; точная причина HTTP 400 неизвестна. Пользователь сообщил о
   восстановлении и пополнении провайдера; это не доказывает причину всех ошибок.
   После сообщения был ещё один ответ Astra, последняя задача использовала advisory.
2. **Нет ожидания advisory после быстрых ошибок.** Проверяется уже готовый файл;
   отдельного ограниченного окна ожидания в замороженной версии нет.
3. **Неверные пути полей в резервном ответе.** В задаче `85e4d703` модель вышла
   по timeout, а своевременный advisory имел четыре `unknown_field`: отсутствовал
   префикс `properties.` у вложенных `parameter_binding` полей. Офлайн-replay
   подтвердил четыре нарушения до исправления и ноль после. Проверка внешнего
   помощника исправлена; это не меняло runner или уже отправленный ответ.
4. **Неполный учёт ошибок чтения.** Перехваченные исключения записаны в trace,
   но не попадают в `EvidenceStore.coverage.failed_results`. 53 timeout посчитаны
   по сырым событиям отдельно; непрочитанные ссылки остаются неизвестными.
5. **Смысловые ошибки при корректных ссылках.** В задачах `0a97c96a`, `532ebd4d`
   malicious не согласовывался с оговорками о недостаточных доказательствах;
   в `454e5006` проигнорирована положительная `digital_signature=valid` при
   null в других полях; в `8c90ca63` попытка записи ошибочно описана как
   подтверждённая запись, а имя файла искажено. Это замечания ревью без эталонных
   классов, а не посчитанные false positive / false negative.
6. **Ограниченная видимость.** До 8 с чтений не обеспечивают полноту графа,
   авторизации, содержимого скриптов или scope реагирования. Повышение качества
   по graded-оценке не измерено до reveal.

## Почему 15 минут недостаточно для надёжного повтора

Текущий расчёт бюджета расследования на задачу:

```text
task_seconds = min(60, (remaining_seconds - 35) / remaining_tasks - 8)
```

Если результат меньше 12 с, запуск quality отклоняется при предварительной проверке.
Для 40 задач и 900 с получается **13,625 с** на расследование; из них 9 с
зарезервированы на финальный RPC, часть остатка расходуется на чтения.
Минимум этой проверки — **835 с (13 мин 55 с)** до учёта создания run; это
технический порог, а не гарантия хороших ответов или завершения всего набора.
В ходе run запас времени проверяется снова.

Фактически последний прогон занял 16:33 и включал 12 неполных ответов.
После восстановления провайдера полноценные ответы могут занимать больше времени.
Поэтому обещать повтор 40 качественных ответов за 15 минут оснований нет.
Для планирования разумно выделять 25–30 минут и сначала измерить задержки короткого
пилота; этот запас — оценка, а не проверенный SLA.

## Как продолжить

1. Исправить учёт read exceptions в coverage и добавить ограниченное ожидание
   identity-matched advisory при быстрых ошибках провайдера.
2. Усилить согласованность вердикта и доказательств: различать неизвестное,
   положительное наблюдение, попытку действия и подтверждённый результат.
3. Провести короткий practice-пилот на восстановленном провайдере, измерить задержки,
   полноту usage и принятые ответы; затем выбирать бюджет полного прогона.
4. После reveal сверить опубликованные оценки с run/task ID и заполнить score,
   не подменяя его числом `terminated`.

Настройка и команды запуска находятся в README. Для нового запуска нужен будущий
`--quality-deadline`: исторический дедлайн 2026-10-10 15:55 нельзя переиспользовать.
При неизвестном исходе remote run нельзя удалять intent ради обхода блокировки.
