# BlueSec Goal Team Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** подготовить и проверить следующую версию BlueSec-агента с контролем доказательств, надёжным harness и измеримым экспериментальным результатом.

**Architecture:** пять ролей с отдельными задачами и конечными goals; один координатор соединяет изменения. Разработчики расследования и harness работают независимо, исследователь выполняет последовательные эксперименты, ревьювер проверяет код и выводы. Сам SOC-агент сохраняет последовательный цикл работы с runtime.

**Tech Stack:** Python >=3.11, Pydantic 2, OpenAI-compatible Chat Completions, существующий gRPC SDK, uv, pytest, Ruff, JSONL.

**Spec:** [2026-10-10-goal-team.md](../specs/2026-10-10-goal-team.md).

Статус: реализация активирована пользователем 2026-10-10; координатор работает в goal. Все новые файлы, интерфейсы и команды ниже — запланированные, если явно не указано обратное.

## Global Constraints

- Python >=3.11; сохранить текущие Pydantic, OpenAI-compatible API, gRPC SDK и uv.lock. Новая тяжёлая orchestration-платформа не требуется.
- Сохранить пять текущих runtime-инструментов и публичную схему NextStep. Проверять совместимость с каталогом текущей задачи; неизвестное обязательное поле должно давать понятную ошибку.
- Сохранить ограничение max_steps от 1 до 100 и default max_tasks=1.
- Все реальные BlueSec-прогоны выполняет единственный владелец экспериментов, последовательно.
- Разделять принятие вердикта, качество расследования, ошибки провайдера, незавершённые задачи и состояние закрытия run.
- Сырые результаты сохранять; сокращать только представление для модели, с явным учётом пропущенных элементов.
- Существование ID или поля не доказывает правильность вердикта либо выбранного IR-действия.
- Использовать только наблюдённые данные инцидента. Частичный журнал не даёт ответов на неизученные ветви графа.
- Не менять `.env` и текущую локальную копию `.env.example` при подготовке команды; ключи не включать в отчёты и новые коммиты.
- Не менять критерии оценки после просмотра результатов; проверочные примеры, использованные для улучшения prompt, больше не считать независимой контрольной выборкой.

## Review Focus

1. Потерян ответ на finish: задача могла завершиться на сервере; нельзя автоматически отправить новый finish или abort с новым идентификатором. Проверки H и C.
2. Упомянутый ID, поле из другого объекта или строка с инструкциями: они не должны становиться наблюдёнными доказательствами. Проверки A и C.
3. Узел с 500 связями: сокращение контекста не должно терять ссылки или скрывать неполноту. Проверки A и E.
4. Отмена во время HTTP/gRPC, ошибка диска и close со статусом closing: нельзя терять исходную ошибку и объявлять run подтверждённо закрытым. Проверки H.
5. Частичная трасса, пропущенный usage или отсутствующий score: нельзя подставлять пустой успешный ответ, нулевую стоимость или нулевую официальную оценку. Проверки E и H.

## 1. Роли, модели и порядок

| Роль | Модель Codex | Владелец результата |
| --- | --- | --- |
| C — координатор | `gpt-6-astra`, `xhigh` | исходная версия, контракты, интеграция, итоговый отчёт |
| A — расследование | `gpt-6-astra`, `xhigh` | доказательства, очередь направлений расследования, компактный контекст |
| H — harness | `gpt-6-astra`, `xhigh` | LLM retries, телеметрия, лимиты, lifecycle и cleanup |
| E — эксперименты | `gpt-6-astra`, `xhigh` | офлайн-набор, анализ трасс, live-пилот, сравнение моделей |
| R — ревьювер | `gpt-6-astra`, `xhigh`, отдельный контекст | независимые замечания и предложения по harness |

Волна 0: C фиксирует исходную версию и интерфейсы; R проверяет критерии измерения.

Волна 1: C + A + H + R. A и H меняют свои файлы; C интегрирует только принятые версии. R получает снимки изменений и тестовые артефакты.

Волна 2: C + E + R + один из A/H для исправлений. E готовит и выполняет проверки; второй разработчик свободен. Слоты меняются по обнаруженным проблемам.

Волна 3: C + E + R. Выпускается отчёт, проверяется рекомендуемая конфигурация, формируется следующий ограниченный цикл улучшений.

Здесь «параллельно» относится к разработке и анализу. BlueSec runtime использует единственный последовательный поток запусков. Ревьювер не отправляет вердикты и не редактирует реализацию за автора.

## 2. Как использовать goal

Goal закреплён за конкретной задачей Codex и задаёт проверяемый результат. Для независимого продолжения у каждого исполнителя должна быть собственная задача с собственным goal. Обычная делегация короткого подзадания сама по себе не означает отдельную долгоживущую goal-задачу. См. [официальное описание Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex).

По последней команде пользователя координатор автоматически создаёт задачи по волнам и передаёт [готовые промпты](../prompts/2026-10-10-goal-team/README.md). Координатор сначала подготавливает общую версию и контракты, затем связывает уже созданные задачи; дубликаты задач не создаёт. Промпты содержат абсолютные пути и правила передачи результатов между worktree. Каждая задача проверяет существующий goal и активирует один конкретный `create_goal(objective=...)`. Численный `token_budget` не задаётся без явного запроса пользователя. Лимиты экспериментальной серии ниже — отдельные ограничения приложения.

Цикл каждого исполнителя: изучить доказательства → выбрать одну проверяемую гипотезу → внести минимальное изменение → проверить → зафиксировать результат → продолжить к следующему критерию. Завершать goal можно только после проверки всех его обязательных результатов. Ожидание другого агента не считается блокировкой. Если без внешнего изменения продолжение невозможно, сохранять точное препятствие; статус blocked использовать по правилам инструмента, после повторения того же препятствия в трёх последовательных goal-ходах.

На передачу координатору: ревизия, изменённые файлы, проверенные гипотезы, команды и результаты, ограничения, пути к артефактам. Рабочие заметки: `reports/goals/C-cycle-01.md`, `A-cycle-01.md`, `H-cycle-01.md`, `E-cycle-01.md`, `R-cycle-01.md` в том же каталоге.

```python
    assert small.omitted_count == 491
    assert {x.object_id for x in full.items if x.kind == "relation"} == set(ids)
```

Часы budget — monotonic. Lock общий для всех рабочих копий этого аккаунта, хранится в одном локальном каталоге, а не внутри каждой worktree.

Поля: attempt_id, requested_model, returned_model если доступен, latency_ms, prompt_tokens, completion_tokens, total_tokens, cached_tokens, reasoning_tokens, finish_reason, outcome, error_type. При провале записи сообщать об этом через stderr и сохранять частичный отчёт, если файловая система ещё доступна. В консоль выводить безопасную диагностику, не сырой malformed-ответ; проверить redaction на искусственном секрете в значениях, ключах JSON и исключениях.

Таймаут не оправдывает выдуманный вердикт. При cancellation выполнять ограниченный cleanup и затем сохранять семантику отмены.

При потерянном ответе CreateRun, closing_acknowledged или другом неоднозначном исходе marker сохраняется даже без run_id, и следующий запуск останавливается до выяснения состояния. ## 6. E — проверки и эксперименты

**Goal для агента E:**

> Построить воспроизводимую проверку следующей версии и провести ограниченный пилот по заранее зафиксированному manifest. Учесть все попытки, сохранить первичные оценки отдельно от незавершений, сравнить версии и модели без выдуманного ground truth. Выпустить отчёт с ограничениями выборки и обоснованным решением о рекомендуемой конфигурации. Офлайн-проверки должны обнаруживать неполный replay и ошибки provenance/lifecycle, а не просто воспроизводить реализацию.

**Владение:** новые `src/bluesec1_agent/evaluation.py`, `scripts/eval_offline.py`, `scripts/compare_runs.py`, `scripts/run_experiments.py`, `tests/test_evaluation.py`, `tests/fixtures/evaluation/`, `reports/experiments/cycle-01/`. Реальные сырые данные остаются в игнорируемом `reports/runs/`; коммитить только обезличенные сводки/синтетические фикстуры.

**Интерфейс:** `summarize_run(trace_path: Path, result_path: Path | None) -> dict[str, Any]` в evaluation.py. Он читает старый trace без schema_version и новый version=2, не смешивает LLM calls, cache hits и remote tool calls. Тестовые драйверы внедряют существующие StructuredStepClient/RemoteTransport, без отдельного сервиса.

- [ ] Сначала написать проверки агрегатора: один accepted+zero-score, один interrupted без score, missing usage, повторная строка попытки, started без finished и отсутствие result.json. Агрегатор обязан сохранить все запуски и не превращать отсутствие в ноль.
- [ ] Подготовить не менее 12 документированных синтетических случаев: вредоносная активность за обычным родителем; легитимная административная команда с положительными доказательствами; только подозрительное имя; 500 связей; цикл; перепутанные ID; неподтверждённое поле; prompt injection в данных; ошибочный ответ инструмента; лимит перед финалом; потерянный terminal-ответ; несовместимый каталог. У каждого случая есть полный доступный граф и отдельные ожидаемые инварианты. Метки benign/malicious явно синтетические.
- [ ] Разделить сценарии, передаваемые разработчикам, и контрольные варианты, которые R/E открывают после заморозки версии. Не добавлять ответы контрольных случаев в prompt агента. Изменённый после просмотра результата вариант считать частью следующего цикла разработки.
- [ ] Исторические трассы использовать для анализа расхода, формы данных и покрытия. Для неизвестного действия replay выдаёт `unsupported_action`, не пустой успешный результат. Результаты replay не объявлять официальным BlueSec score.
- [ ] Создать manifest с фиксированными конфигурациями, версиями, порядком, лимитом попыток и правилами остановки. Перед live требуется прохождение офлайн-gates и ревью R. В этой фазе не менять одновременно модель и поведение, если затем заявляется причинный эффект отдельного изменения.

Manifest после ревью неизменяем. Резервирование слота, фактическое выполнение и итоговые статусы записываются отдельно в `reports/experiments/cycle-01/attempts.jsonl`; они не изменяют SHA-256 manifest. Ошибка надёжной записи резервирования запрещает начинать новый CreateRun. Сводка сопоставляет запланированные слоты manifest с журналом всех попыток.

Предлагаемый пилот первой итерации: **максимум 16 попыток задач**, включая прерванные и неудачные; max_tasks=1, max_steps=60, timeout задачи 900 с и cleanup 30 с. Это выбранный масштаб исследовательской серии, а не запрос бесконечного расхода.

| Этап | Количество | Конфигурация и назначение |
| --- | ---: | --- |
| Проверка работоспособности | 4 | v2 harness: по одной задаче на gpt-6-luna, gpt-6-astra, claude-opus-5-5, gpt-6.1-sol |
| Сравнение поведения | 6 | общий новый instrumentation: по 3 задачи baseline/v2 стратегии на gpt-6-luna, чередуя порядок |
| Сравнение сильных моделей | 6 | v2: по 2 дополнительные задачи на gpt-6-astra, claude-opus-5-5, gpt-6.1-sol, чередуя модели |

Baseline стратегии — сохранённое поведение до A, но с одинаковой телеметрией и cleanup H. Такое сравнение оценивает пакет изменений расследования; отдельные компоненты требуют последующих ablation-экспериментов. Первые четыре задачи служат проверкой работоспособности; не использовать их для подбора prompt и затем как независимые контрольные результаты.

Нет подтверждённого механизма заказать один и тот же live-инцидент. Поэтому сравнение live — непарное, с малой выборкой; фиксировать доступные характеристики задач и порядок запуска. Не обещать статистически доказанного победителя после 16 попыток. Официальную точность классов/precision/recall не вычислять без истинных меток.

Правило рекомендации фиксировать в manifest до запуска: этот малый пилот сам по себе не меняет рабочую модель по умолчанию. Для следующей исследовательской серии кандидат допускается, если у него есть три принятых финала с известным quality_score, проверяемыми ссылками и подтверждённым cleanup, без открытых P1/P2. Среди допущенных кандидатов порядок: медиана quality_score по убыванию, затем efficiency_score по убыванию при полной доступности этого поля, затем медиана walltime по возрастанию. Полное равенство означает отсутствие предпочтения. При нулевых оценках у всех, неполных данных или прерванной серии рекомендовать сначала разбор причин и дополнительную выборку, а не смену модели. Такой порядок определяет следующий эксперимент, а не доказывает превосходство модели.

- [ ] Остановить серию при неизвестном состоянии активного run, проблеме авторизации, несовместимой схеме или двух последовательных инфраструктурных сбоях. Сохранить неполную серию и причину; неиспользованные слоты отметить not_started. Слот попытки расходуется до CreateRun, даже если run_id не получен. Rate limit повторять только в рамках настроенного deadline/backoff; успешные попытки не подменяют неудачные в manifest. Автоматически возобновлять остановленную серию ради заполнения квоты нельзя.
- [ ] Исправимый дефект вернуть A/H через C и закончить отчёт о текущей серии. После исправления следующий цикл получает отдельный manifest и ревью; предыдущие результаты не исчезают. При внешнем препятствии E выпускает частичный отчёт с точным blocker. Отчёт о неудачном эксперименте может быть завершён; непроверенное улучшение и готовность к live-запуску при неизвестном server state — нет. C сверяет завершение своего goal со всеми обязательными критериями, не меняя их задним числом.
- [ ] Для каждой попытки сохранять: конфигурацию, run/task IDs, результат протокола, качество/эффективность/reward если сервер вернул, walltime, remote calls, LLM attempts, repairs, локальные отказы provenance, токены и полноту usage, cleanup. Денежную стоимость считать только при известном тарифе провайдера; пользовательские ×-коэффициенты не считать ценой.
- [ ] Выпустить таблицу всех попыток, отдельно распределения по завершённым задачам и частоту незавершений по всем попыткам. Для отсутствующих scores указать количество; не улучшать среднюю оценку молчаливым удалением failures. Малые группы показывать отдельными значениями и медианой, без убедительных на вид p95 на трёх задачах.

Запланированные команды после реализации скриптов:

```bash

uv run python scripts/eval_offline.py --fixtures tests/fixtures/evaluation --output reports/experiments/cycle-01/offline.json
```

## 8. Завершение цикла и следующий шаг

- [ ] C проверяет чистоту diff и общий набор тестов на интегрированной версии.
- [ ] R подтверждает проверку конкретной ревизии и перечисляет оставшиеся ограничения.
- [ ] E предоставляет полный учёт попыток и объясняет, какие выводы данные поддерживают.
- [ ] C передаёт пользователю одну рекомендуемую команду запуска, пути к отчётам, список исправлений и три следующих эксперимента в порядке пользы.

Первый следующий эксперимент выбирается по фактам: например, если много времени уходит на repair — форматы/лимиты генерации; если потеряны направления расследования — очередь и контекст; если доказательства корректны, а официальные оценки низки — стратегия расследования и модель. В следующем цикле менять одну причину за эксперимент.

План не включает переобучение, внешнюю векторную базу, сложный supervisor-framework или несколько LLM на каждый шаг инцидента. Их добавление требует наблюдаемой проблемы и отдельного сравнения с текущим простым циклом.

Инструменты ruflo/ToolSearch, упомянутые в пользовательском AGENTS.md, в текущей сессии не обнаружены. План использует доступные задачи Codex, goals и делегацию; установка дополнительного framework для первой итерации не требуется.
