## Запрос и результат первой итерации

Пользователь просит план работы нескольких автономных агентов в режиме goal и отдельного ревьювера, который предлагает улучшения harness. Допускаются дорогие модели. Работа носит исследовательский характер: выяснить, какие изменения помогают расследованию и какая обвязка для этого нужна.

Команда улучшает существующего SOC-агента. Первая итерация должна дать проверяемые доказательства в расследовании, ограниченный и наблюдаемый цикл исполнения, воспроизводимые проверки и отчёт по экспериментам. Утверждение о росте качества допускается только по результатам измерений. Отрицательный результат эксперимента также сохраняется.

Этот документ и связанный план описывают будущую работу. Их подготовка не активирует goals и не запускает новые инциденты.

## Границы первой итерации

- Python >=3.11; сохранить текущие Pydantic, OpenAI-compatible API, gRPC SDK и uv.lock. Новая тяжёлая orchestration-платформа не требуется.
- Сохранить пять текущих runtime-инструментов и публичную схему NextStep. Проверять совместимость с каталогом текущей задачи; неизвестное обязательное поле должно давать понятную ошибку.
- Сохранить ограничение max_steps от 1 до 100 и default max_tasks=1.
- Все реальные BlueSec-прогоны выполняет единственный владелец экспериментов, последовательно.
- Разделять принятие вердикта, качество расследования, ошибки провайдера, незавершённые задачи и состояние закрытия run.
- Сырые результаты сохранять; сокращать только представление для модели, с явным учётом пропущенных элементов.
- Существование ID или поля не доказывает правильность вердикта либо выбранного IR-действия.
- Использовать только наблюдённые данные инцидента. Частичный журнал не даёт ответов на неизученные ветви графа.
- Не менять `.env` и текущую локальную копию `.env.example` при подготовке команды; ключи не включать в отчёты и новые коммиты.
- Не менять критерии оценки после просмотра результатов; проверочные примеры, использованные для улучшения prompt, больше не считать независимой контрольной выборкой.

## Команда и модели

Пять ролей: координатор, разработчик расследования, разработчик harness, исследователь экспериментов, независимый ревьювер. Одновременно работают не более четырёх исполнителей, включая координатора. Исследователь занимает освободившийся слот после первой волны разработки.

Для Codex-разработчиков и ревьювера выбрать `gpt-6-astra`, reasoning `xhigh`, из доступного в этой сессии набора. Для самого SOC-агента сравнивать доступные через пользовательский шлюз `gpt-6-astra`, `claude-opus-5-5`, `gpt-6.1-sol`; текущий `gpt-6-luna` оставить базовым вариантом. Названия и множители шлюза не доказывают реальную стоимость или превосходство модели.

## Критерии результата

1. Исходные проверки проходят; новые проверки воспроизводят и закрывают перечисленные в плане дефекты.
2. Ненаблюдавшиеся ID и поля блокируются до отправки финального ответа.
3. Ошибки, повторы, лимиты и cleanup видны в структурированных артефактах; отсутствие usage не превращается в нулевую стоимость.
4. Офлайн-набор проверяет механику на полном синтетическом графе; неполнота исторических журналов отражается явно.
5. Все попытки согласованного live-пилота учтены, версии и конфигурации зафиксированы, результаты не выбраны из удачных запусков.
6. Ревьювер проверил итоговую версию и выпустил список улучшений harness с доказательствами, приоритетом и способом измерить эффект.
7. Итоговый отчёт отделяет исправленную механику от гипотез о росте SOC-качества. Новая конфигурация становится рекомендуемой только при достаточных основаниях; иначе сохраняется предыдущая.
